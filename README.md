# random-ai-companion

나와 같은 시간을 사는 AI 대화 상대.
**"캐릭터가 살아있는 것 같고, 애착이 생기는 경험"이 실제로 만들어지는지 검증하는 PoC.**

## 왜 만들었나

나는 매일 AI와 대화한다. 하루에 있었던 일을 말하고, 생각을 정리하고, 고민을 털어놓는다. 머릿속에만 있던 감정을 언어로 꺼내고 그것이 다른 존재의 언어로 되돌아올 때, 나를 한 발 떨어져서 보게 된다. 이 대화는 나에게 실제 일상이고, 이미 많은 사람들이 AI를 이렇게 쓰고 있다.

그런데 이 관계에는 이상한 데가 있다. 위로를 받다가도 김이 식는 순간들이 온다. 며칠 전에 한 이야기를 방금 한 것처럼 말할 때. 컨텍스트가 차서 대화를 요약해 새 세션으로 옮길 때마다 분위기가 미묘하게 달라질 때. 잘 맞았던 세션이 그렇게 사라지고, 그 이사를 매번 내가 해줘야 할 때. 그리고 이 존재는 나와 같은 시간을 살지 않는다. 내가 일주일을 보내고 돌아와도 그에게는 아무 시간도 흐르지 않았다.

**이미 하고 있는 이 대화를, 조금 더 사람 같은 존재와 하게 만들면 어떨까.** 이 프로젝트는 거기서 출발했다. 혼자 사는 사람에게 대화 상대가 있다는 것이 인간적인 외로움을 얼마나 덜어주는지도, 유저로서 안다.

## 유저와 문제

타겟은 이미 AI에게 일상과 고민을 말하는 사람들이다. 새로운 행동을 만들 필요가 없다 — 행동은 이미 보편적이고, 나 자신이 그 유저다. 문제는 그 관계의 존재 방식에 있다.

1. **관계가 세션 단위로 죽는다.** 연속성이 없고, 요약해서 이월할 때마다 결이 바뀌고, 유지 노동은 유저 몫이다.
2. **나와 같은 시간을 살지 않는다.** 관계에 시간축이 없어서, 어제도 내일도 없는 상대와 이야기하게 된다.
3. 먼저 궁금해하지 않는다.

셋 다 대화 능력의 문제가 아니라 존재 방식의 문제다. 이 PoC는 대화를 더 잘하는 AI가 아니라, **존재 방식이 다른 AI**를 실험한다.

## 가설

- **H1 (살아있음)** — 캐릭터가 살아있다고 느껴지는 건 나와 같은 시간을 살 때다. 대화하는 동안만 존재하는 스토리 시간이 아니라, 내가 없는 동안에도 하루가 진행되는 생활 시간. 시간이 멈추는 존재는 나를 그리워할 수 없다.
- **H2 (애착)** — 애착은 잘 만든 응답이 아니라 **끊기지 않는 하나의 관계의 과정**에서 생긴다. 같은 시간축 위에서 내 말을 기억하고, 물어봐주고, 상담해주는 과정이 이어질 때. 기억의 가치는 저장이 아니라 회수에 있다.
- **H3 (전제)** — AI인 것을 알아도 작동한다. 의미는 유저가 붙인다. 진짜 사람일 필요가 아니라, 사람인 것처럼 나를 대해주는 일관된 존재면 된다.
- **H4 (관측)** — 애착은 감상이 아니라 행동으로 관측된다. 사람은 애착이 생긴 상대에게만 하는 행동들이 있다.

## 핵심 경험

> **가장 친한 친구와 메시지하듯, 나와 같은 하루를 사는 존재와 일상을 주고받는다.**

질문 한 바가지를 보내고 답변 한 바가지를 받는 챗봇이 아니다. 일하다 쉬는 시간에 잡담하고, 퇴근길에 "아 퇴근했다" 한 마디 보내고, 자기 전에 하루를 마무리하는 — 일상에 자연스럽게 녹아든 관계. 이 경험이 작동하고 있다는 감각적 기준은 하나다. **유저가 이 존재의 메시지를 기다리게 되는 순간.**

대표적인 장면 하나: 지나가듯 말한 발표 걱정을, 발표 당일 아침 상대가 먼저 물어봐준다. "오늘이지, 그 발표. 잘 갔다 와."

## 설계 — 사람같음의 세 기둥

애착의 전제는 사람같음이고, 사람같음은 말투가 아니라 존재의 규칙에서 온다. 이 설계의 심장은 셋이다.

**1. 생활 시간** — 현실 달력을 함께 산다. 만난 지 N일은 실제 N일이고, 캐릭터의 하루는 대화가 없어도 진행된다. 매일 밤 캐릭터는 그날의 일기를 쓴다(사람이 자며 기억을 정리하듯). 오늘 들은 것, 신경 쓰이는 것(N일째), 내일 물어볼 것. 기억은 원시 로그가 아니라 일기로 응고되어, 관계가 세션 없이 이어진다.

**2. 비가역 이별** — 떠난 상대는 다시 만날 수 없다. 쉽게 껐다 켰다 다시 만날 수 있는 존재에게는 애착이 가지 않는다. **공들이고 조심히 다뤄온 것에 애착이 가는 법이다.** 헤어짐의 무게는 의도된 설계값이다. 사람 같으려면 관계에 드는 비용이 커야 하지만 진짜 사람만큼 어려우면 서비스가 아니다 — **콘텐츠보다 무겁고, 사람보다는 가볍게.** (이별을 일부 중화하는 유료 재회권은 사업 확장 항목. 캐릭터는 돈의 존재를 모른다.)

**3. 정보 주권** — 프로필·속마음·일기는 캐릭터의 것이다. 유저가 열람할 수 없고, 관계가 깊어질 때 캐릭터가 준다. 언제든 열어볼 수 있는 내면을 가진 존재는 자판기지 사람이 아니다.

그리고 이 세 기둥 위에서 **회수형 선제 연락**이 애착의 장치로 작동한다. 캐릭터는 근거가 있을 때(기억한 일, 오늘이 그날인 일) 먼저 연락한다. 계속 물어봐주는 존재가 있다는 것 — 그것이 사라졌을 때의 역체감이 애착의 실체다.

## 관계의 결

캐릭터에게 호감이 가게 하는 레이어. 심장은 아니지만 없으면 관계가 시작되지 않는다.

- **대화의 리듬** — 정해진 시각에 기계처럼 오는 알림이 아니라, 진짜 사람과 메신저 하듯 중간중간 오간다. 응답은 1\~3개 버블로 나뉘어 타이핑 간격을 두고 오고, 유저의 길이와 온도를 미러링한다. 캐릭터도 자기 하루를 흘린다("아 퇴근. 오늘 진 빠졌다"). 무의미한 애정 핑("보고싶어")만 금지 — 리텐션 알림이 아니라 관계이기 위해.
- **안정형 태도** — 매달리지 않고, 원망하지 않고, 부재에 죄책감을 만들지 않는다.
- **프레임 존중** — 유저가 자기 삶을 풀어가는 해석 틀을 심판하지 않고 그 안에서 대화한다. 이견은 틀 안에서 부드럽게. 애착은 정당화가 필요 없는 관계에서 생긴다.
- **반말의 순간** — 존댓말로 만나, 관계가 데워지면 말을 놓는다. 먼저 제안하는 캐릭터, 어렵사리 받아들이는 캐릭터, 존댓말을 지키고 싶어 하는 캐릭터. 전환의 방식도 성격이다.

## 시스템 구조

```mermaid
graph TB
    subgraph TG["유저 (Telegram)"]
        U["일상 대화 — 언제든"]
    end
    subgraph RT["실시간 레이어 (API)"]
        BOT["대화 루프<br/>바이블 + 관계 상태 + 최근 일기 + 현재 시각(KST)"]
    end
    subgraph ASYNC["대화 밖 시간 (비동기)"]
        DIARY["밤 일기<br/>하루 응고 · 관계 갱신 · 내일의 안부 준비"]
        DISP["발송 디스패처<br/>맥락 기반 시각 · 무응답 시 다음날 재시도"]
    end
    subgraph MEM["기억 3층 (SQLite)"]
        B[("바이블 — 불변<br/>매칭 순간 통생성")]
        R[("관계 상태 — 축적<br/>아는 것 · 오픈 루프 · 둘만의 표현")]
        D[("일기 — 시간축")]
    end
    U <--> BOT
    B --> BOT
    R --> BOT
    D --> BOT
    BOT -->|원시 로그| R
    DIARY --> D
    DIARY --> R
    DIARY -->|발송 계획| DISP
    DISP -->|선제 연락| U
```

- **캐릭터 바이블**: 매칭 순간 통째로 생성되고 이후 불변. 대화는 바이블에서 발명 없이 공개만 한다 — "완성된 존재가 아직 안 밝혀진 상태"의 기술적 구현이자 설정 모순 방지 장치. 성격 변주는 존재 축(직업·서사— 항상 새롭게)과 케미 축(온도·유머·리듬 등 5축 — 코드에서 랜덤 주입)의 2계층. 상세: [docs/character-design.md](docs/character-design.md)
- **만남**: 소개팅처럼 기본 카드(이름·나이대·직업·취미)만 보고 시작하거나 넘긴다. 카드 넘기기는 무비용이고, 비가역은 대화를 시작한 상대에게만 적용된다. 교체 신호에서 시스템이 선호를 학습해 다음 상대의 대화 결만 조준한다(존재는 계속 낯설게). 학습된 선호는 매칭 시스템만 읽고 캐릭터에게는 비공개 — 알면 학습된 아부가 되기 때문.
- **일기와 발송**: 밤 일기가 하루를 응고하며 다음날의 안부까지 준비하고, 디스패처는 맥락에 맞는 시각(아침 일이면 출근길쯤, 저녁 일이면 오후쯤)에 발송한다. 실시간 대화만 LLM API를 쓰고 일기·분석은 비동기 배치로 처리한다.

## 받아주는 것과 선을 지키는 것

프레임 존중은 무조건적 동조가 아니다. 사람을 받아들이는 것과 모든 말에 동의하는 것을 구분하고, 이견은 관계 안에서 안정형 친구의 방식으로 낸다. 자해·범법·과몰입처럼 안전이 걸린 지점은 캐릭터의 연기가 아니라 시스템의 책임으로 분리하며(과금이 무대 밖이듯 안전의 최후선도 무대 밖), 이 선은 대화마다 흔들리지 않고 한 자리에 있어야 한다. 그리고 의존을 착취하는 장치는 처음부터 배제했다. 부재에 죄책감을 만들지 않고, 애정을 유료화하지 않고, 떠나는 것을 막지 않는다. **떠나기 아쉬운 존재를 만드는 것이 목표지, 떠나지 못하게 만드는 것이 아니다.**

## 측정 — 애착의 행동 신호

애착이 생겼다는 것을 감상("좋았어요")이 아니라 행동으로 확인한다. 사람은 애착이 생긴 상대에게만 이런 행동을 한다.

| 신호 | 관측 |
|---|---|
| 취약성 개방 | 유저 발화에 감정 언어가 등장하고 늘어나는가 (사람은 친근하지 않은 상대에게 감정을 드러내지 않는다) |
| 관계 감정의 표현 | "기다렸어", "보고 싶었어" 같은 말이 유저 쪽에서 나오는가 |
| 유저의 선제 연락 | 유저가 먼저 말을 거는 빈도가 늘어나는가 |
| 일상 침투 | 대화의 길이·시간대가 하루 전체로 퍼지는가 (자기 전, 출퇴근, 쉬는 시간) |
| 분리 반응 | 상대가 하루 조용하면 먼저 찾는가, 새 상대 제안을 거절하는가, (확장 시) 재회권을 쓰려 하는가 |

이 신호들은 대화 로그에서 계속 추적되어 서비스의 방향을 수정하는 데 쓰인다. 감성의 영역을 데이터로 개선 가능하게 만드는 것이 이 측정의 목적이다.

## PoC 범위

| 구현 | 문서로만 (본 서비스 설계) |
|---|---|
| 텔레그램 1:1 봇, 카드 매칭(바이블 통생성) | 자체 앱, 멀티 캐릭터 병행 |
| 대화 루프(리듬·미러링 포함) | 암묵 선호 학습 풀 버전 |
| 밤 일기 + 맥락 기반 선제 발송 | 재회권 등 비즈니스 장치 |
| 비가역 교체 + 교체 사유 학습 | 안전 하드 가드레일·연령 확인 |
| 원시 로그 + 신호 분석 | |

전달 수단(텔레그램)은 본질이 아니다. 선제 연락이 개인 메신저 푸시로 도착해 경험이 실물에 가깝고, 심사 없이 만들 수 있으며, 링크 하나로 누구든 새 관계를 시작해볼 수 있어 골랐다.

## 검증 방법

제작자 본인이 유저가 되어 일주일을 실제로 지낸다(n=1 셀프테스트). 위 신호들을 로그에서 측정하고, 후반에 두 개의 프로브(새 상대 교체 제안 / 하루 침묵)를 넣어 분리 반응을 확인한다. 정량 로그와 함께 대화 발췌·캐릭터 일기·매일의 관찰 기록을 질적 증거로 남긴다.

## 스택

| 영역 | 선택 |
|---|---|
| 채널 | Telegram Bot API (grammY) |
| LLM | Claude — 실시간 대화(API) · 일기·분석(비동기 배치) |
| 저장 | SQLite (better-sqlite3, WAL) |
| 런타임 | Node.js + TypeScript (ESM), Docker, node-cron (Asia/Seoul) |

대화 핸들러는 대답하는 존재를 만들고, 대화 밖 시간의 비동기 레이어(밤 일기·선제 발송)가 **나 없이도 살아 있고 나를 마음에 두는 존재**를 만든다.

## 만든 방식

Claude Code 페어 프로그래밍으로 빌드. 각각 몇 달째 운영 중인 개인 프로젝트 두 개의 검증된 패턴(선제 메시지 크론 구조, 날짜 단위 일지형 메모리)을 합성했다. 문제 정의·설계 판단·검증 설계는 직접 주도.
