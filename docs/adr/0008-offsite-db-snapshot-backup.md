# ADR-0008: DB를 6시간마다 스냅샷으로 떠서 VM 밖에 보관하기

## 상태

Accepted

## 맥락

[0007](0007-keep-sqlite-single-file.md)에서 SQLite 파일 하나와 단일 VM 구성을 유지하기로 하면서, VM 밖으로 나가는 백업을 그 결정의 조건으로 걸어 뒀다. 그때까지 백업은 배포할 때마다 손으로 뜬 스냅샷이 전부였고 그 사본마저 같은 VM 안에 있어서, VM을 잃으면 마지막 배포 이후의 대화가 함께 사라진다.

보험을 드는 위험은 디스크 손상이 아니라 VM 전체 상실이다. 컨테이너 하나가 데이터 디렉터리를 바인드 마운트로 들고 있고 DB는 WAL 모드로 도는 파일 하나인데, 이 파일을 그냥 복사하면 WAL에만 있고 본체로 아직 옮겨지지 않은 내용이 빠져 복원이 깨진다. 그래서 어떤 방식으로 사본을 뜰지가 첫 갈래였다.

## 결정

6시간마다 일관된 스냅샷을 떠서 압축한 뒤 오브젝트 스토리지로 올린다.

- 스냅샷은 컨테이너 안에서 SQLite 온라인 백업 API로 뜬다(`src/tools/backup-db.ts`). 봇이 도는 중에 실행해도 안전하고 WAL 내용까지 함께 담긴다. 뜬 자리에서 무결성과 외래키를 검사하고 표별 행 수를 로그에 남겨, 나중에 복원한 DB와 대조할 기준으로 쓴다.
- 호스트 크론이 스크립트를 실행한다(`scripts/backup-db.sh`). 컨테이너에서 파일을 꺼내 zstd로 압축하고 rclone으로 올린다. 이미지를 바꾸지 않고 상시 프로세스도 늘리지 않는다.
- 보존은 3단이다. 6시간 스냅샷은 7일, 하루 한 개는 30일, 주 한 개는 26주를 남긴다. 승격은 그날 몫과 그 주 몫이 아직 없을 때만 하므로, 실행을 한 번 걸러도 다음 실행이 알아서 메운다.
- 실패하면 슬랙으로 알리고 주 1회 정상 요약도 같은 채널로 보낸다. 크론이 조용히 멈추는 경우는 실패 알림에 걸리지 않고 요약이 끊기는 것으로 드러난다.
- 저장은 이 프로젝트만 쓰는 버킷에 두고 그 버킷에만 닿는 토큰을 쓴다. 보존 기간이 지난 파일을 지우는 명령이 사람 없이 도는 자리라, 경로를 잘못 적어도 다른 프로젝트의 백업까지 지우지 못하게 막아 둔다.

## 대안

**WAL을 이어서 복제하기(Litestream 계열).** 복원 지점이 초 단위까지 좁혀지지만 상시 프로세스가 하나 늘고, DB 파일을 계속 잡고 있으며, 복원에 전용 도구가 필요하다. 지금 드는 보험은 VM 전체 상실이라 6시간이면 충분하고, 복원할 때 압축만 풀면 그대로 DB 파일인 쪽이 다루기 쉽다고 생각했다.

**파일을 그대로 복사해 올리기.** 가장 간단하지만 WAL에 있는 내용이 빠져 복원이 깨진다. 봇을 멈추고 복사하면 정합성은 맞아도 6시간마다 대화가 끊긴다.

**같은 VM 안에 세대를 남기기.** 지금 상태와 다를 게 없다. 위험이 VM 상실이라 같은 호스트에 남긴 사본은 함께 사라진다.

## 결과

최악의 경우 잃는 대화가 6시간치로 줄어든다. 압축한 스냅샷 하나가 200KB 남짓이고 세대를 다 합쳐도 20MB를 넘지 않아 보관에 드는 용량은 신경 쓸 규모가 아니다.

감수하는 것은 복원 지점의 거칠기다. 6시간 안에 오간 대화는 되살릴 수 없고, 그보다 촘촘하게 복원해야 할 일이 생기면 WAL 복제로 갈아타야 한다. 그때 건드릴 자리가 호스트 크론과 스크립트 하나뿐이라 되돌리는 비용은 크지 않다.

복원은 올라간 파일을 내려받아 압축을 풀고 검사 명령으로 확인한 뒤 데이터 디렉터리에 놓으면 끝난다. 이 절차는 백업을 붙이는 시점에 실제로 한 번 돌려서 무결성과 외래키, 표별 행 수가 원본과 맞는 것을 확인했다.
