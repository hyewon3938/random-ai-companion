# ADR-0004: 유저 선호를 캐릭터에게 공개하고 저장 자리를 세 갈래로 나누기

## 상태

Accepted (2026-08-27)

## 맥락

원래 설계는 유저의 선호를 매칭 시스템만 읽고 캐릭터에게는 비밀로 했다. 캐릭터가 유저의 취향을 알면 비위를 맞추는 말만 하게 된다는 걱정에서 나온 원칙이다.

그런데 실제 대화에서는 상대가 내 취향을 알고 맞춰 주는 것 자체가 관계의 자연스러운 부분이고, 유저도 자기가 좋아하는 것을 캐릭터가 기억해 주기를 바란다. 정말 경계할 것은 근거 없이 비위를 맞추는 쪽인데, 그건 아부 금지 stance 규칙이 이미 막고 있다. 게다가 무작위 매칭이 유저 입력 생성으로 바뀌면서(ADR-0002) 비밀 선호의 유일한 독자였던 매칭 시스템이 사라져, 원칙을 유지하면 선호를 아무도 읽지 않게 된다.

## 결정

선호를 캐릭터에게 비밀로 하는 원칙을 버리고, 아부 금지는 stance 규칙으로 계속 지킨다. 선호가 놓이는 자리는 셋으로 가른다.

- **대화용은 relationships의 잘 통하는 것(rapport) 컬럼.** 둘이 함께 좋아하게 된 것, 유저가 좋아해서 캐릭터가 기억하는 것이 여기 쌓이고, 관계 항목이라 프롬프트에 항상 들어간다.
- **측정용은 운영 로그 집계.** 유저가 어떤 대화에 오래 머무는지 같은 신호는 캐릭터가 아니라 운영자가 보는 값이라, 저장소를 따로 두지 않고 로그에서 계산한다.
- **유저 단위 선호는 user_preferences 테이블.** 특정 캐릭터와 무관하게 유저라는 사람이 가진 선호를 담는 자리다. 매칭 전용이던 옛 뜻을 이 뜻으로 바꾸고, 지금은 자리와 뜻만 정해 둔다. 채우는 일은 유저가 여러 캐릭터를 만드는 구조가 생길 때, 그동안 쌓인 대화 원문과 관계 기록에서 뽑는다.

## 대안

**비공개 원칙 유지하기.** 아부 위험이 원천에서 막힌다. 하지만 읽는 곳이 없는 값을 계속 추출하게 되고, 캐릭터가 유저의 취향을 끝까지 모르는 관계는 오래 이어질수록 부자연스럽다. 아부는 취향을 숨기는 대신 태도 규칙으로 막는 쪽이 관계를 해치지 않는다.

**user_preferences 테이블 없애기.** 지금 읽고 쓰는 코드가 없으니 지워도 동작은 같다. 하지만 여러 캐릭터를 만드는 구조가 오면 캐릭터 밖의 유저 단위 자리가 다시 필요해지고, 빈 테이블 하나를 두는 비용은 없다시피 하다. 뜻만 바꿔 남긴다.

**유저 단위 선호를 지금부터 채우기.** 데이터가 미리 쌓인다. 하지만 읽는 코드가 없는 값을 쌓으면 기준이 바뀔 때 통째로 버리게 된다는 것을 케미 축에서 MBTI로 축을 바꾸며 이미 겪었다. 읽는 쪽이 생길 때 그 시점의 산 기록에서 뽑는 쪽이 낭비가 없다.

## 결과

선호를 따로 추출하는 배치는 계속 멈춰 두고, 기존 user_preferences의 값은 지우지 않되 새 뜻으로 재사용하지도 않는다.

잘 통하는 것 컬럼은 생성 때 비워 두고 새벽 정리가 대화에서 채운다. 캐릭터가 유저의 취향을 알게 되는 만큼, 아부 금지 stance가 실제로 지켜지는지는 대화 채점에서 볼 항목이 된다.
