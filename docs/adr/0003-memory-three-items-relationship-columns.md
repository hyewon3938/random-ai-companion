# ADR-0003: 기억을 세 항목으로 통합하고 관계는 컬럼으로 분리하기

## 상태

Accepted (2026-08-27) — 관계 항목 중 관계의 결은 [ADR-0010](0010-character-attitude-in-identity.md)이 대체

## 맥락

지금 저장 항목은 정체성 · 유저 사실 · 진행 중인 일 · 관계처럼 여럿으로 갈려 있고, 캐릭터 쪽인지 유저 쪽인지가 항목 이름에 박혀 있다(user_fact). 그래서 같은 성질의 데이터가 주인에 따라 다른 항목이 되고, 유저의 진행 중인 일처럼 이름이 없는 조합은 저장할 자리가 애매하다. 주변 인물은 별도 테이블이라 기억과 검색 경로가 두 곳으로 갈린다.

반대로 관계는 항목이 미리 정해져 있고 한 캐릭터에 한 행뿐이며 둘 사이의 상태라 주인을 나눌 수 없어서, 키와 태그로 자리를 찾는 기억 구조에 넣으면 정해진 항목을 매번 검색으로 꺼내는 셈이 된다.

## 결정

memory_items의 저장 항목을 사실(fact)·진행 중인 일(ongoing)·주변 인물(person) 셋으로 줄이고, 각 항목에 주인(owner) 컬럼으로 캐릭터 쪽인지 유저 쪽인지를 따로 표시한다. 세 항목 곱하기 주인 둘의 여섯 조합이 전부 유효하고, 어느 조합인지는 모델이 저장할 때 내용을 보고 정한다. 주변 인물 테이블(cast_members)은 person 항목이 대신하므로 없앤다.

캐릭터와 유저 사이의 관계는 기억에 넣지 않고 relationships 테이블의 컬럼 여덟 항목(사이 정의 · 말투 · 서로 부르는 말 · 관계의 결 · 잘 통하는 것 · 조심할 것 · 만나 온 이야기 · 마음 상태)으로 저장한다. 여덟 항목 전부를 프롬프트에 항상 넣는다.

세부 판단 5가지:

- **출처(origin)는 creation과 conversation 둘이고, 저장 함수가 creation 행의 수정을 거부한다.** 생성 때 정한 큰 정체성은 바꾸지 않는다는 원칙을 문서가 아니라 쓰기 코드가 지키게 했다. 씨앗을 뜻하던 옛 이름 seed는 컨디션 시드(day_seeds)와 헷갈려서 creation으로 바꿨다.
- **person 항목은 키의 무엇 자리에 사람 이름이 들어간다.** 이름은 태그와 같은 문자열이라, 이름 태그 하나로 그 사람의 행과 관련 일기·일정이 같이 검색된다. 같은 주인 쪽에서 같은 이름이면 영역이 달라도 같은 사람으로 합치고, 동명이인은 이름을 늘려(회사 민수) 가른다.
- **추가 정보는 항목마다 화이트리스트로 막는다.** person은 어떤 사이·만나는 방식·사는 곳·마지막 등장, ongoing은 끝나는 조건이고, fact는 비워 둔다. 목록에 없는 필드는 저장 코드가 버려서, 필드를 늘리는 일이 설계 변경으로만 가능하다.
- **감정은 기억에 저장하지 않는다.** 그날의 감정은 일기가, 유저를 향해 이어지는 마음은 relationships의 마음 상태 컬럼이 담는다. 기억에 감정이 섞이면 사실 검색에 지난 감정이 끼어든다.
- **관계 갱신은 자리를 나눈다.** 말투와 마지막 연락 시각은 답장 파이프라인이 그때그때 쓰고, 나머지 항목은 새벽 정리가 쓴다. 관계 갱신은 기억을 정리하는 호출의 출력에 같이 들어 있어서 모델 호출 수가 늘지 않고, 마음 상태는 최근 일기에 뚜렷한 근거가 있을 때만 바꾼다.

## 대안

**항목을 잘게 유지하기.** 항목 이름이 내용을 설명해 줘서 읽기는 쉽다. 하지만 주인이 이름에 박히면 항목 수가 주인 수만큼 배로 늘고, 저장할 때 어느 항목인지 고르는 판정도 그만큼 늘어난다. 성질(사실인가, 진행 중인가, 사람인가)과 주인을 축 둘로 가르면 항목 셋으로 전 조합이 표현된다.

**관계도 기억 항목으로 넣기.** 저장 구조가 하나로 통일된다. 하지만 관계는 항목이 미리 정해져 있고 전부 항상 프롬프트에 들어가야 해서 태그 검색으로 꺼내는 구조의 장점을 하나도 쓰지 않으니, 정해진 항목은 컬럼에 두는 쪽이 맞다.

**주변 인물 테이블 유지하기.** 옮기는 비용이 없다. 하지만 인물도 기억과 같은 키·태그 동작(이름으로 자리 찾기, 태그로 관련 기록 모으기)이 필요해서, 테이블이 갈리면 같은 검색을 두 곳에 구현하게 된다.

**관계 변화 로그 테이블 만들기.** 마음 상태가 변해 온 과정이 남는다. 하지만 캐릭터 시점의 하루 기록은 일기가 이미 매일 남기고 있어서, 로그 테이블은 같은 이야기를 두 번 적는 자리가 된다. 변화의 근거는 일기에서 찾는다.

## 결과

스키마가 바뀌고 지금 데이터를 옮겨야 한다. 컬럼 추가와 삭제, 값 이름 바꾸기, cast_members 행의 person 이관이 필요해서, 구현 세션 계획을 이 변경 앞에 다시 짠다.

프롬프트 조립은 관계 여덟 항목을 relationships에서 읽어 항상 넣고, 기억은 지금처럼 태그로 검색한다. 새벽 정리의 출력 스키마에 관계 항목이 추가되지만 호출 수는 평소 4번 그대로다.
