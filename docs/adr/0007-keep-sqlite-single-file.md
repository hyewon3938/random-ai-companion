# ADR-0007: SQLite 파일 하나와 단일 VM 구성을 유지하기

## 상태

Accepted

## 맥락

모델 호출 원본을 남기기 시작하고([ADR-0006](0006-llm-call-log-storage.md)) 슬랙 트레이스를 붙이면서
저장소를 나눌 때가 됐는지 다시 보게 됐다. 운영 DB 사본을 표별로 재어 보니 답이 분명했다.

| 표 | 크기 | 행 수 | 쌓인 기간 |
|---|---|---|---|
| `prompt_blobs` | 389KB | 103 | 23시간 |
| `messages` | 258KB | 1,618 | 50일 |
| `trace_events` | 213KB | 91 | 23시간 |
| `day_plans` | 197KB | | 50일 |
| `diary_entries` | 106KB | | 50일 |
| `llm_calls` | 25KB | 34 | 23시간 |
| 전체 | 1.57MB | | |

**관측용 세 표의 하루치가 대화 기록 50일치보다 2.4배 크다.** 전체의 40%를 하루 만에 차지했고,
그중 `trace_events`는 보존 기간이 없는 유일한 표다. 대화가 쌓여서 DB가 커지는 게 아니라
관측 데이터가 커지는 구조라서, 나눈다면 어디를 먼저 나눠야 하는지가 여기서 나온다.

지금 구성은 `better-sqlite3`에 WAL 모드, DB 파일 하나, 사양이 작은 단일 VM에 컨테이너 하나다.
프로세스는 이미 둘이다. 봇 밖에서 도는 새벽 정리가 같은 파일을 열고, 곧 읽기 전용 대시보드가 셋째로 붙는다.
`src` 안에서 문장을 실행하는 자리는 31개 파일에 251곳이고, 전부 동기 호출이다.

판단 근거를 갖추려고 국내외 캐릭터챗 서비스 6곳이 어떤 저장소를 쓰는지 조사했다
(회사별 상세는 저장소 밖 조사 기록에 있다). 공개 자료에서 확인한 공통점은 셋이다.
대화 원문을 어디에 쌓느냐를 병목으로 지목한 곳이 없고, 저장소를 나눈 기준은 규모가 아니라 접근 패턴이며,
비용을 말할 때는 저장이 아니라 프롬프트 크기를 말한다.
누적 다운로드 120만에 연매출 3,000만 달러 규모에서도 대화 로그를 주 트랜잭션 DB에 그대로 두고
대화방 단위 조회와 읽기 개수 상한으로만 비용을 묶은 사례가 있다.

## 결정

SQLite 파일 하나와 단일 VM 구성을 유지한다. 세부는 여섯 가지다.

- **SQLite를 유지한다.** 쓰기량이 유저 1,000명 기준으로도 초당 1~2건이라 감당할 양의 1% 수준이고,
  동기 API 덕분에 251개 실행 지점이 `await` 없이 돌아가며, 백업이 파일 복사로 끝난다.
  네트워크 왕복이 0이라는 점은 셋 중 가장 덜 중요한 이유다. 관리형 DB로 옮겨서 지금 얻을 것이 없다.
- **대화 기록을 별도 저장소로 빼지 않는다.** 조사한 서비스가 저장소를 안 바꾸고 해결한 방법이
  대화방 단위 조회와 개수 상한인데, 이 프로젝트는 `idx_messages_chat (chat_id, sent_at)` 인덱스와
  최근 40개 상한으로 이미 같은 모양이다. 누적이 늘어도 답장 조립 비용은 그대로다.
- **관측용 데이터가 분리 1순위지만 지금은 파일 하나에 둔다.** `llm_calls`·`prompt_blobs`·`trace_events`는
  답장 경로가 아니라 나중에 들여다보는 용도라 접근 패턴이 이미 갈렸고, 회사들이 로그부터 갈라낸 순서와 같다.
  다만 총량이 아직 작아서 파일을 나누는 대신 **보존 기간을 먼저 붙인다.**
  본문 90일 정리는 `llm_calls`·`prompt_blobs`에만 걸려 있고 `trace_events`는 빠져 있다.
- **나눠야 할 때가 오면 엔진이 아니라 파일을 나눈다.** 관측용 표만 별도 `.db` 파일로 옮기고 `ATTACH`로 붙이면
  쓰기 잠금이 갈리면서도 조인은 그대로 쓸 수 있다. 엔진을 바꾸는 것보다 되돌리기 쉽다.
- **연속 백업을 SQLite 유지의 조건으로 둔다.** 파일 하나라는 장점은 그 파일이 사라지면 그대로 단점이 된다.
  VM 밖으로 나가는 연속 백업이 붙기 전까지는 이 구성을 안전하다고 말하지 않는다.
- **서버를 옮긴다면 이유는 성능이 아니라 복구 가능성이다.** 지금 사양으로 부하가 문제 된 적이 없다.
  옮길 이유는 재시작이 실패했을 때 기댈 곳이 있느냐이고, 그건 사양을 올리는 문제가 아니라 돈을 내는 문제다.
  옮기더라도 DB 구성 변경과 같은 회차에 하지 않는다. 둘을 묶으면 무엇이 원인인지 가릴 수 없다.

## 대안

- **관리형 PostgreSQL로 이전.** 251개 실행 지점을 비동기로 바꿔야 하고 그 함수를 부르는 자리까지 연쇄로 번진다.
  얻는 것은 지금 필요 없는 동시 쓰기와 네트워크 왕복이다. 유저가 늘어 쓰기가 겹치기 시작하면 그때 다시 본다.
- **로그만 다른 엔진으로 분리.** 조사한 서비스들이 실제로 한 일이지만, 그쪽은 하루 1억 건대의 적재를 다루고
  분석 파이프라인이 따로 있었다. 하루 100행대에서 엔진을 하나 더 세우면 운영할 것만 늘어난다.
- **libSQL·Turso 같은 SQLite 호환 원격 DB.** 코드를 거의 안 고치고 원격으로 옮길 수 있지만,
  동기 API가 비동기로 바뀌어서 결국 같은 포팅 비용이 든다. 옮길 이유가 생겼을 때 후보로 남겨 둔다.
- **지금 미리 옮겨 두기.** 나중에 어차피 옮길 거라면 지금이 제일 싸다는 논리인데,
  아직 서비스를 시작하지 않아서 어떤 쿼리가 무거워질지 모른다. 모르는 상태로 고른 구조가 더 비싸다.

## 결과

**좋아지는 것.** 배포가 컨테이너 하나로 끝나고, 백업이 파일 복사이며, 로컬에서 운영 사본을 그대로 열어
리허설을 돌릴 수 있다. 지금까지 스키마를 다섯 번 옮기면서 매번 운영 사본으로 먼저 검증할 수 있던 것이 이 구성 덕분이다.

**감수하는 것.** 쓰기는 한 번에 하나뿐이라, 프로세스가 셋으로 늘면 대기 시간에 기대게 된다.
지금은 새벽 정리가 하루 한 번 짧게 쓰고 대시보드는 읽기만 해서 겹칠 일이 거의 없지만,
대시보드에 쓰기가 생기면 이 전제가 깨진다. VM이 통째로 사라지면 DB도 함께 사라지므로 연속 백업이 없는 동안은 위험을 안고 간다.

**다시 판단할 신호.** 아래 중 하나라도 걸리면 이 기록을 다시 연다.

- 쓰기 대기로 답장이 밀리는 경우가 로그에 잡힐 때
- DB 파일이 500MB를 넘어 백업·복사가 부담이 될 때
- 대시보드나 다른 프로세스에 쓰기 경로가 생길 때
- 캐릭터가 여러 개가 되어 한 VM에 안 들어갈 때

되돌리려면 `src/db.ts`의 연결 부분과 251개 실행 지점, 그리고 그 위에 얹힌 트랜잭션 18곳을 함께 손봐야 한다.
