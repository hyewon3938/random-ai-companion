# ADR-0001: 기억 구조 스키마를 한 번에 다시 만들어 옮기기

## 상태

Accepted (2026-08-26)

## 맥락

대화에 쓰는 기억을 지금은 `relationships.state_json` 한 덩어리에 넣고, 필요한 값을 꺼낼 때마다 JSON 전체를 프롬프트에 넣어 왔다. 주제별로 골라 넣을 수가 없어 프롬프트가 계속 커지고, 같은 사실이 여러 번 들어가도 걸러지지 않는다. 새 설계는 기억을 항목·키·태그로 나눠 저장하고 대화 주제에 맞는 것만 검색해서 넣는다.

옮겨야 할 것이 3가지다. 새 저장 항목을 담을 테이블이 6개 새로 필요하고, 쓰던 테이블 13개는 컬럼 이름과 저장하는 값이 바뀌며, 값이 정해진 컬럼에는 CHECK를 걸어 틀린 값이 들어오지 못하게 막아야 한다. 그런데 SQLite는 이미 있는 테이블에 CHECK와 UNIQUE를 붙이지 못한다. 지금 스키마는 `CREATE TABLE IF NOT EXISTS`와 그때그때 붙인 `ALTER TABLE ADD COLUMN` 가드로 쌓여 왔고, 운영 중인 데이터베이스의 `user_version`은 0이다.

봇은 텔레그램 long polling으로 혼자 동작해서 배포할 때 잠깐 멈춘다. 데이터베이스 파일은 볼륨으로 붙어 있어 배포로 사라지지 않는다.

## 결정

테이블 정의를 코드 한곳의 표에 모으고, 그 표로 새 데이터베이스를 만들거나 옛 데이터베이스를 옮긴다. 봇이 시작할 때 `PRAGMA user_version`이 1보다 낮고 옛 컬럼이 남아 있으면 마이그레이션을 한 번 실행한다.

바뀌는 테이블마다 이름을 옛 이름으로 바꿔 두고(`ALTER TABLE x RENAME TO x__old`) 새 정의로 다시 만든 다음 값을 옮기고 옛 테이블을 지운다. 이름 바꾸기, 컬럼 추가, 값 바꾸기가 한 번에 끝난다. 이름을 바꾸는 동안에는 `legacy_alter_table`을 켜서 자식 테이블의 `REFERENCES` 절이 따라 바뀌지 않게 한다. 전체를 트랜잭션 하나로 묶고, 끝에서 `foreign_key_check`로 확인한 뒤 `user_version`을 1로 올린다. 한 군데라도 실패하면 전부 되돌리고 옛 스키마가 그대로 남는다.

세부 판단 4가지:

- **값이 정해진 컬럼은 영어 식별자로 저장하고 CHECK로 막는다.** 답장 여건·활동 성격·발송 종류·누구 쪽·출처처럼 목록이 닫혀 있는 값이 대상이다. 한국어 표시 이름은 화면에 내보내는 곳에서 한 번만 붙인다. 모델이 짓는 값(키의 무엇, 태그, 저장하는 내용, 영역 이름)은 한국어 그대로 둔다.
- **컬럼 이름은 별칭 없이 바꾼다.** `SELECT sent_at AS ts`처럼 옛 이름을 남기면 타입 검사가 놓치는 자리가 생겨서, 실제로 이름을 바꿔 모든 접근 지점이 타입 검사에 걸리게 했다.
- **옛 JSON 덩어리는 `legacy_state_json`으로 이름만 바꿔 남긴다.** 기억을 새 테이블로 옮기는 일은 다음 단계 몫이라, 옮길 원본을 지우지 않는다.
- **아직 값을 알 수 없는 컬럼은 기본값으로 채운다.** 일정의 출처는 지금 값에서 알아낼 수 없어 전부 대화로 두고, 유저가 아는지 여부는 전부 모름으로 둔다. 둘 다 다음 단계에서 바로잡는다.

설계 문서와 다르게 둔 것도 3가지 있다. 유저 프로필의 나이대 컬럼은 지금 프롬프트가 읽고 있어 생년과 함께 남겼다. 나이대에서 생년을 계산할 수 없어 온보딩을 고칠 때까지는 두 컬럼이 함께 있다. 새로 만든 프로필 컬럼(이름·성별·생년·직업·사는 곳)은 설계상 필수지만 채울 값이 없어 NULL을 허용했다. 원래 있던 갱신 시각 컬럼도 이 재생성에서 NOT NULL이 빠져서, 나중에 프로필 컬럼들과 함께 제약을 다시 걸어야 한다. 대화 중 붙잡은 일정을 담던 테이블과 사실 포착 워터마크는 읽는 코드를 걷어내는 단계까지 그대로 둔다.

## 대안

**컬럼마다 ALTER로 고치기.** 지금까지 해 온 방식이고 코드가 짧다. 하지만 SQLite에서 CHECK와 UNIQUE를 나중에 붙일 수 없어 값을 막는 장치를 포기해야 한다. 이번 개편은 저장하는 값의 종류를 바꾸는 일이라, 틀린 값이 들어오는 것을 데이터베이스가 막아 주는 쪽이 이후 단계에서 훨씬 안전하다.

**새 파일을 만들어 옮기고 갈아 끼우기.** 옛 파일이 통째로 남아 되돌리기 쉽다. 대신 두 파일 중 어느 쪽이 진짜인지 관리해야 하고, 봇을 멈춘 채 옮겨야 한다. 데이터가 작아서 트랜잭션 하나로 충분하고, 되돌리기는 배포 직전 백업으로 해결된다.

**옛 이름을 두고 코드에서만 새 이름 쓰기.** 배포가 가벼워지지만 저장된 이름과 코드의 이름이 갈라진다. 앞으로 몇 단계 더 스키마를 손대야 해서, 어휘가 둘로 갈려 있으면 매번 어느 쪽 이름인지 확인해야 한다.

## 결과

스키마를 손보는 다음 단계들은 이 표에 정의를 추가하고 버전을 올리기만 하면 된다. 새 테이블 6개는 아직 아무도 읽지 않아서, 이번 배포는 스키마만 바뀌고 봇의 동작은 그대로다.

되돌리려면 배포 직전에 뜬 백업으로 파일을 되돌리고 이전 이미지로 다시 세운다. 마이그레이션이 중간에 실패하면 트랜잭션 하나로 묶어 둔 덕에 전부 되돌아가지만, 성공한 뒤에 되돌리는 코드는 없다.

코드와 데이터베이스를 함께 배포해야 한다. 옛 코드가 새 스키마를 읽으면 컬럼 이름이 맞지 않아 실패한다.

타입 검사는 SQL 문자열 안의 컬럼 이름을 보지 못한다. 그래서 코드에 있는 SQL 문장을 전부 뽑아 옮긴 데이터베이스에 걸어 보는 검사를 따로 돌렸고, 타입 검사가 통과한 뒤에도 7군데가 걸렸다. 이 검사는 다음 단계에서도 다시 쓴다.

기록에 남는 발송 종류 하나는 규칙으로 갈랐다. 침묵 팔로업은 밤 인사와 낮의 근황 둘로 나뉘는데 옛 기록에는 구분이 없어서, 보낸 시각이 새벽 5시 이전이면 밤 인사로 봤다. 지난 기록을 세는 통계에서 이 값을 쓸 때는 추정이라는 것을 알고 써야 한다.
